# The Founder's Playbook：构建 AI 原生创业公司

Anthropic 于 2026 年 5 月发布的 36 页创业指南，系统梳理 [[ai-native-startup]] 的四个核心阶段（Idea → MVP → Launch → Scale），阐述如何将 Claude Chat、Claude Cowork 和 [[claude-code]] 作为创业基础设施，在极少人手的前提下构建可规模化的公司。核心论断：AI 已抹平技术壁垒，创业瓶颈从"能不能建"转变为"该不该建、该建什么"。

## 创始人角色的三大转变

传统创业假定成长路径是：验证 → 融资 → 招聘 → 构建 → 再融资 → 增长 → 再招人 → 循环。AI 已抹去了"每个新阶段都需要更大团队、不同技能和新一轮融资"的预设。[[ai-native-startup]] 极度精简（通常只有创始人一人），在规模化前就可能达到产品验证、早期营收甚至盈利。

**三大 AI 能力柱：**

1. **对话智能与研究（Conversational Intelligence）**：相当于各领域全天候顾问。竞争分析、市场规模测算、投资备忘录起草、PRD、战略 devil's advocate——以前的答案是"找一个懂的人"，现在是直接用 AI。
2. **代理编码（Agentic Coding）**：用自然语言描述 → AI 生成、测试、调试、重构。工程时间不再是限制瓶颈，非技术创始人也能交付生产级软件。
3. **工作流自动化（Workflow Automation）**：CRM 更新、周报编制、文档同步、合规追踪——这些原本压在创始人身上的"运营税"可以自动化消除。

最根本的转变：创始人角色从"执行者"（个人贡献者）变为"Agent 调度员"（Orchestrator）——生成想法并指挥系统（AI Agent、工具和小团队）来执行这些想法。注意力上移到高阶工作：产生想法、把关方向、判断边界。

## Idea 阶段：验证优先，构建其次

**目标**：研究导向的验证——在投入资源构建之前，确立真实问题存在且解决方案有效的证据。

**退出标准**（三个问题全部回答"是"）：
1. 问题是否真实且具体？（能说出：谁遭遇、多频繁、多严重、现在如何应对）
2. 解决方案是否对准了验证揭示的真实问题（而非最初假设）？
3. 是否有足够信号证明构建 MVP 是理性决策而非信仰行为？

**三大陷阱**：

**陷阱一：将构建误认为验证。** Agentic coding 让原型构建极快，但原型的存在本身不是验证。历史上 42% 的创业公司死于没人需要的产品；现在这个比例将上升，因为"有想法 → 立刻有原型"的距离几乎为零。解法：原型是与用户对话的道具，真实证据来自对话本身。

**陷阱二：过早规模化。** AI 会以完全相同的热情为糟糕的想法和伟大的想法生成代码——判断力在你，不在 AI。在问题-解决方案契合验证之前就加速执行，会把更多资源投入错误方向。

**陷阱三：确认偏误有了研究引擎。** 让 AI 验证你的创业想法，它会找到支持证据；让它估算市场规模，它会找到让 TAM 显得可融资的数字。解药：用同一工具做对抗性分析——主动要求 AI 找出反对你想法的最强证据。

**Claude 的 Idea 阶段用法**：
- 将问题陈述磨砺成可测试假设（"合同审查太慢" → "中型企业内法律团队因红线通过邮件而非版本控制文档管理，每次审查周期需 3+ 天"）
- 竞争格局四层分析：直接竞争者、间接竞争者、潜在收购方、邻近进入者——要求 AI 论证每个威胁为什么会击败你
- 趋势分析：识别未来两年内的法规/技术/人口统计趋势顺风或逆风
- 客户访谈设计：正确问题（问过去行为而非未来意向）、正确对象（精确职位/公司类型/资历）、正确顺序
- 每 5 次访谈后：支持假设的证据 vs 挑战假设的证据，然后请 AI 质疑这种不对称是否真实反映数据
- 使用 Claude Cowork 自动化联系人列表构建、个性化外联邮件序列、Gmail/Google Calendar 集成日历协调

> **贯穿全生命周期的核心用法**：用 Claude 做结构化 devil's advocate——这在每个阶段都是必要工具。

## MVP 阶段：边建边留下上下文

**目标**：将验证过的问题转化为真实用户会使用的产品，同时为 Launch/Scale 阶段保持代码库的可持续性。

**退出标准**：获得真实的产品-市场契合（PMF）证据——留存（Retention）、付费（Revenue）或推荐（Referral）。

**四大陷阱**：

**陷阱一：代理技术债务（Agentic Technical Debt）**。传统技术债务是渐进的，可以规划偿还；AI 技术债务是指数级的——没有规格文档和架构上下文，每次会话重新推导基础设计决策，决策漂移，代码库失去连贯的心智模型。最终代码虽能运行，但结构不连贯，在真正需要迭代时崩溃。

**解法**：**CLAUDE.md 作为会话持久记忆**。在任何生产代码开始前，用 Claude 定义并记录架构原则、要避免的依赖、有意识接受的权衡。将这份文档保存为 `CLAUDE.md` 文件，放在项目目录中。Claude Code 自动读取它作为会话上下文。每次会话结束后更新。目标是"一个你能解释清楚结构的代码库，而不仅仅是能跑的代码库"。

**陷阱二：虚假 PMF（False Product-Market Fit）**。启动能量来自早期用户的朋友、投资组合公司、HN 头条——这些不能预测第 6 周或第 12 周的表现。解法：在第一个用户到来之前就定义留存基准、激活标准、D7/D30 目标，以及什么样的数据模式构成真实 PMF 而非乐观噪音。

PMF 判断工具：
- **Sean Ellis 测试**："如果无法再使用这个产品，你会有什么感受？" → >40% 回答"非常失望"= 有意义的 PMF 信号
- **努力测试**：PMF 前，留存需要持续的外联、激励和创始人能量（推动）；PMF 后，产品本身开始自我驱动留存（拉动）

**陷阱三：零摩擦功能蔓延（Zero-Friction Scope Creep）**。每个新功能都"只要一个下午"——这让每次添加在当时都显得合理，但产品会在边界不清的情况下扩张。解法：构建开始前写好范围文档，将决策点从"应该建吗？"变成"是否有足够真实用户需求证明这值得建？"

**陷阱四：由无经验导致的安全漏洞**。Agentic coding 生成能用的代码，不一定是安全的代码。功能要么有要么没有，但安全漏洞是不可见的，直到被利用才暴露。在任何真实用户触碰前必须做安全审查：认证和会话处理、API 响应中的数据暴露、输入验证和注入风险、已知漏洞的依赖项。

**MVP 阶段 Claude Code 工作流**：
- 每次会话开始时：提供 CLAUDE.md 架构上下文文档 + 本次会话的具体任务
- 每次会话结束时：更新 CLAUDE.md（记录决策、新的假设）
- 把每次会话视为执行已经做出的产品决策，而非"再加点新东西"的机会

**无法到达 PMF 时**，用 Claude 做诊断：
- 数据中是否有一个细分群体的表现与其他人不同？
- 设计价值与用户体验价值之间的差距是定位问题还是产品问题？
- 当前产品要找到真实 PMF 需要哪些前提成立，这些前提在现有数据下现实吗？

## Launch 阶段：从创始人驱动到系统驱动

**目标**：将早期牵引转化为可重复、可持续的增长引擎，同时将代码库强化为生产就绪状态，并在产品周围建立真正的公司。

**三个退出标准**：
1. 增长可重复且渠道驱动——知道 CAC、LTV、回收期
2. 产品能处理生产工作负载——基础设施强化、安全合规就绪、可靠性在真实生产条件下稳定
3. 运营不再依赖创始人——流程存在，自动化到位，创始人不是每个流程的触发点

**四大挑战**：

**挑战一：技术债务兑现**。为速度和验证而构建的 MVP 代码，在生产流量、新功能和增长复杂度的压力下暴露缺陷。解法：Claude Code 做全架构审计（脆弱点、难维护的快捷方式、测试覆盖薄弱处），然后用 Claude 对修复工作做优先级排序（下一个发布前必须修什么、可以等一个 Sprint、可以接受为持续债务）。

**挑战二：创始人成为瓶颈**。该花 1 小时的决策要等一周；支持请求因为只有你知道答案而堆积；运营任务只有你记得时才发生。解法：审计你目前亲自处理的所有事务，分类为（a）可以完全自动化、（b）需要人但不必是你、（c）真正需要创始人判断。

**挑战三：安全合规不再可推迟**。真实用户、真实数据、潜在企业合同——安全漏洞从理论风险变为真实暴露。要求：系统性安全合规审查在生产规模到来之前，不是之后。Claude Code 可扫描 SOC 2、GDPR、HIPAA 相关漏洞。

**挑战四：扩张过早**。进入与原始市场有实质差异的新市场，引入新用户行为、合规要求、支付基础设施——变量太多，无法清晰解读自己的数据，同时冒着忽视原始用户群的风险。

**Launch 阶段 Claude 用法**：
- Claude Code：架构审计 → 修复优先级排列 → 将 MVP 时期只在头脑中的架构决策写入 CLAUDE.md
- Claude Cowork：运营负载审计 → 自动化工作流设计 → 实现并运行（Sprint 调度、Bug 路由、周报编制）
- Claude：设计轻量产品管理流程（Sprint 节奏、最小 Spec 模板、Bug 分流决策树、周报格式）

## Scale 阶段：护城河与面向公众的执行官

**目标**：建立系统性增长；构建可审计、可防御的护城河；从构建者转变为面向公众的执行官。

**退出阈值**（三选一）：可持续盈利 / IPO 就绪 / 被收购——三种形式都要求增长系统化可审计，产品护城河经得起外部审查，组织成熟且可持续运营。

**四大挑战**：
1. **将运营层真正移交**：先搞清楚只有你才能做的事（产品叙事决策、董事会关系、企业交易、创始人对创始人的对话），其余全是委托或 Claude Cowork 自动化候选
2. **企业级技术基础设施**：日志、监控、事件响应工具、可观测性层、SLA 可执行化——大客户签多年合同前要看到这些
3. **有机增长的天花板**：早期靠创始人销售、Product Hunt、个人关系，这个模式有上限。需要真正的 GTM 职能：市场细分、消息架构、分析师关系、销售手册
4. **规模化组织职能**：招聘、薪酬、会计、法务运营——无论团队多小都需要

**护城河三重奏**：

**第一重：领域专业知识 → 产品特异性**。创始人的领域知识（行业黑话、监管地雷、真实边缘案例）通过 Claude 被编码进产品逻辑——竞争对手无法直接复制这种积累。用 Claude 将创始人知识转化为可复用的结构化上下文（技能、工作流、边缘案例测试套件）。

**第二重：用户行为数据 → 飞轮**。用户接受哪些输出、拒绝哪些，形成行为指纹（Behavioral Fingerprint）——这是时间锁定的（Time-locked）、情境特定的（Context-specific），后来者无法购买。每次改进使产品更有用 → 驱动更多使用 → 产生更多反馈 → 驱动更多改进。

**第三重：工作流锁定（Workflow Lock-in）**。用户在产品上构建了自动化、培训了团队成员、连接了数据源和其他工具——切换从产品决策变成全面运营项目。深度锁定来自：API、Webhook、SDK（让客户在你的产品上构建），以及原生集成（连接目标用户依赖的数据管道和项目管理工具）。

**Scale 阶段 Claude 用法**：
- Claude：构建 GTM 基础资产（市场细分、消息架构、分析师关系策略、销售手册、投资人指标叙事）
- Claude Cowork：执行层（内容管线、外向序列、分析师简报物流、PR 节奏、CRM 卫生、管道报告）
- Claude Code：构建演示环境、集成文档、Sandbox 租户、API 参考、技术单页纸；构建企业支持基础设施（日志、监控、可观测性）

## 三大 Claude 产品矩阵

这是贯穿四个阶段的工具选择框架：

| 任务类型 | 工具 | 特点 |
|---------|------|------|
| 快速问答、即兴头脑风暴、小任务 | Claude Chat | 快速、对话式、无需设置 |
| 研究分析、输出完整文档（需访问文件/系统） | Claude Cowork | 文件夹访问、MCP 连接器（Gmail/GCalendar/Notion 等）、定时任务 |
| 编写/测试/调试/发布软件 | Claude Code | 代码库访问、Diff、Git 集成、开发环境 |

三者共用同一个底层 Claude 模型；区别在于围绕它的工作空间。随着公司从 Idea 发展到 Scale，三个工具的使用比例会演变——但最终是互相增强的：Claude Code 的审计结果输入给 Claude 做分析，Claude 的分析结果驱动 Claude Cowork 的自动化。
