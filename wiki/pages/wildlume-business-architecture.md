# 曜野业务架构

> 本文档是 2026-05-20 对话推演的沉淀产物。基于 The Founder's Playbook（Anthropic）的启发，结合曜野的实际业务情境，梳理出业务架构与价值链的全景骨架。
>
> **本版本范围**：参与者图谱、战略骨架、价值主张、信息流盘点
> **下一版本（v2）应深挖**：资金流、产品流、信息流剩余类（中游/上游）的深挖、反哺机制 B/C/D/E 方向

---

## 一、参与者图谱

### 1.1 价值链上下游

- **上游**：6 家活跃供应商（浙江/福建/广东工厂）
- **中游**：4 家公司主体
  - 深圳曜野科技 —— 采购、出口、退税
  - 香港曜野国际贸易 —— 海外利润中心、结汇
  - 宁夏曜野商贸 —— 不退税分销商通道
  - 香港林德贸易 —— 备用
- **下游**：4 个股东的运营团队作为分销商（陈伟军（代持陈海军）、柴继云、吕海锋）
- **终端**:C 端消费者（Amazon DE 为主 + TEMU + 速卖通）
- **服务侧**:海外仓（乐歌 DE / 谷仓 DE / 乐丰 FR / 乐丰 IT）+ 货代（堡森/乐丰/美通）

### 1.2 关键结构性事实

**曜野的客户 = 曜野的股东**。除张昊鹏外的 3 位股东共同持有 70% 股份，每人各自带运营团队，他们是曜野唯一的分销商群体，货盘不对外。

这个结构的含义：

1. 客户结构封闭、不可拓展（除非引入新股东）
2. 利益绑定深度异常
3. 增长天花板 = 股东运营团队的扩张能力 + 各团队的运营效率
4. "客户反馈"与"董事会决议"高度重合

## 二、战略骨架

| 维度 | 内容 |
|------|------|
| 定位 | 供应链服务公司（实际面对 C 端）|
| 起源 | 股东能力互补，共同攻克中大件赛道 |
| 演化方向 | 合作社平台 → 张昊鹏主导的专业供应链公司 |
| 组织哲学 | 业务体量庞然大物 + 组织 orchestrator-only |
| 品牌策略 | 双层结构（公司品牌层 + 运营品牌层）|
| 工厂策略 | 从采购商升级为研发合作伙伴 |
| 数据策略 | 聚合分销商运营数据 = 独立性基础设施 |

### 2.1 定位：供应链服务公司（实际面对 C 端）

虽然商业模式是 B2B2C，但**曜野要用 C 端思维做产品和供应链决策，用 B 端思维做交付和结算**。客户与用户在结构上分离：

- **客户**（付费方）：分销商。衡量曜野的指标是利润率、库存周转、缺货率、退货率
- **用户**（消费者）：C 端。衡量产品的指标是质量、价格、物流体验、售后响应

**C 端是因，B 端是果**：C 端满意度直接决定 B 端的运营结果。

| 维度 | 表层理解（B2B） | 实际含义（面对 C 端）|
|------|----------------|---------------------|
| 选品 | "分销商觉得能卖什么" | "C 端为什么会买、买完会怎么评价" |
| SKU 池规模 | SKU 数量、款式覆盖 | C 端真实需求的覆盖度 |
| 产品质量标准 | 出厂合格率 | C 端差评率、退货率、Amazon 评分 |
| 数据能力 | 进销存数据 | C 端评论、搜索词、退货原因、平台算法变化 |
| 内容能力 | 产品规格表 | Listing copy、A+ Content、图片视频 |
| 售后体系 | 出库后责任划清 | 退货流、差评应对、售后体验闭环 |

### 2.2 起源：股东能力互补 + 共同攻克中大件

曜野不是市场机会驱动，而是合作社平台模式：

- 4 个股东各自在不同品类有销售能力
- 谁也无法单独承担中大件供应链的能力门槛和资金门槛
- 中大件在运输和采购上有特殊壁垒，本身就是赛道护城河

### 2.3 演化方向：股东退出准备

"未来其他股东可能慢慢退出，最终由张昊鹏掌控"——这是关键战略假设。隐含含义：

- 必须在那个时点到来之前，把 SKU 池、分销商关系、平台运营经验沉淀为**曜野自己的资产**
- **数据回流机制是曜野独立性的基础设施**（不是锦上添花）
- 没有数据回流，股东退出时曜野会失去 C 端洞察

### 2.4 组织哲学：orchestrator-only 团队

未来曜野可能依然只有 5-8 个真人员工，但每个真人都是 AI orchestrator 级别。

实现路径组合（路径 3 + 2 + 1）：

- **路径 3（主线·运转方式）**:用 AI 工具放大单人能力
- **路径 2（反馈闭环方式）**:追踪分销商运营链接 + 售后反馈聚合
- **路径 1（组织扩张方式）**:未来招人 = 招与张昊鹏同等级的 orchestrator（一人 + N 个 AI 员工），而不是专业分工的执行者

预见的挑战：

- 人才市场是空白的——传统招聘渠道里几乎不存在
- 管理和文化是新问题（orchestrator 之间怎么协作、怎么不重复劳动）

### 2.5 品牌策略：双层结构

- **公司品牌层（B 端）**:wildlume / 曜野——对应分销商、供应商、海外仓、货代、平台后台等 B 端合作方
- **运营品牌层（C 端）**:未来注册的新品牌——对应 Amazon Listing、A+ Content、消费者认知

**当前 Amazon Listing 挂 wildlume 是"过渡状态"**。短期不为 wildlume 做 C 端品牌投入；ERP 字段设计需要预留双层结构（一个 SKU 既属于公司品牌，又可能挂在不同的运营品牌下）。

### 2.6 工厂策略：三层升级

1. 优质采购商（订单 + 付款条件）
2. 生产链条优化
3. **研发深度合作**（曜野参与产品开发，C 端洞察反向输入工厂）

### 2.7 数据策略：数据回流是独立性基础设施

单个分销商只看自己的 Amazon 后台，曜野通过聚合 4 个分销商的运营数据 + 售后数据，反而拥有比任何单个分销商都完整的 C 端视图。这本身就是曜野对分销商的核心价值之一，且随着 SKU 池扩大和数据沉淀**会复利增长**。

## 三、价值主张

### 3.1 对分销商

- 中大件供应链的运输/采购门槛单股东无法独立承担
- "集中力量办大事"——共同探索中大件赛道
- 跨分销商运营数据的全景视图洞察（曜野独有）

### 3.2 对 C 端

- 当前曜野完全隐形（通过分销商触达）
- 未来即使自建运营也不用"曜野"品牌，注册新品牌
- 曜野始终是供应链主导者，不出现在 C 端面前

### 3.3 对供应商

工厂关心订单和付款条件。曜野的目标：

- (a) 成为工厂端优质采购商
- (b) 优化与工厂的整个生产链条和配合度
- (c) 寻找能研发、能开发、能提供更优质产品的工厂进行深度合作

## 四、信息流盘点

### 4.1 上游信息 —— 工厂端

| 子项 | 状态 |
|-----|------|
| 产品规格 | 来自工厂报价单/样品（Excel/PDF），曜野手动录入 ERP；规格变更靠业务员主动微信通知 |
| 工厂库存 | 工厂不开放，需要时靠微信/电话问 |
| 生产排期 | 下单前工厂告知预计交期，记录在 ERP 采购单备注；变更靠业务员告知 |
| 报价 | Excel/微信发，曜野手动录入 ERP；历史回看靠 ERP 采购单 |
| 出货时效 | 货代告知曜野，手动登记 |
| 质检数据 | 到货时抽检，问题反馈靠微信回传工厂，无结构化沉淀 |

**主要断点**：工厂库存完全黑盒；产品规格变更无 push 通道；工厂业务员是单点信息节点。

### 4.2 中游信息 —— 曜野自身

| 子项 | 状态 |
|-----|------|
| 采购单 | ERP 已有采购模块；与工厂的确认/变更沟通在微信，未回流到 ERP |
| 出口/清关单据 | 报关单、提单、装箱单、发票分散在邮件、货代 PDF、报关公司文件里 |
| 海外仓库存 | ERP 已有海外仓模块；4 家海外仓数据格式不一致，能 API 对接但仍需人工盘点（**出现过丢货**）|
| 头程物流 | **ERP 暂无模块**；实时跟踪靠货代微信发截图 |
| 财务数据 | 开票、应收应付、退税进度分散在财务软件、Excel、ERP 多处 |
| 多主体协同 | 4 家公司之间的内部往来（采购货款、利润转移、外币结汇）靠人工 |

**主要断点**：单据散落多处无统一归档；海外仓信任度（丢货）；头程物流模块空白；财务和业务数据可能割裂；多主体协同对账成本高。

### 4.3 下游信息 —— 分销商运营

| 子项 | 状态 | 完整度 |
|-----|------|-------|
| 订单/销量 | ERP 已能让分销商绑定平台店铺、自动拉取订单、做 SKU 绑定 | 90% |
| 退货数+原因 | ERP 已有售后模块（绑定订单），但目前不够完善 | 40% |
| 评论 | 分销商各自在后台看，差评在群里吼一声；无结构化沉淀 | 0% |
| 广告 ACoS | 各分销商各投各的，策略不共享 | 0% |
| Listing 状态/BSR/排名 | 分销商各自盯，曜野还没主动追踪 | 0% |
| 平台政策变化 | 哪个 SKU 遭警告/下架靠分销商主动告知 | 0% |

**主要断点**：评论/退货原因无结构化提炼；广告效率跨分销商不可比；4 个分销商数据无聚合视图。

**关键判断**：API 是技术问题不是授权问题。最终目的是拉所有平台运营数据，先从订单衍生数据开始，提前预留接口/字段/权限。

### 4.4 终端信息 —— C 端

| 子项 | 状态 |
|-----|------|
| 购买行为 | 完全在 Amazon 后台，曜野不接触 |
| 评论内容 | 分销商看，但可能只看数量不挖内容 |
| 退货原因 | Amazon 标签 + 买家自述；目前看数量有分类但不明确 |
| 售后咨询 | 买家发 Amazon 站内信，分销商应答；曜野不接触 |
| 复购/再访 | 完全黑盒 |
| 场景使用反馈 | 买家上传的视频评测/图片评价散落在 Listing 下，无人系统收集 |

**主要断点**：曜野与 C 端之间隔着分销商 + 平台两层，反馈损耗最大；评论文本是金矿但没人挖；退货原因未反向输入工厂研发。

**关键判断**：
- 物理上的数据获取没有大问题——下游补全 + 复购 hash（地址+收件人模糊匹配，70-85% 准确度）+ 行为/场景画像基本到位
- 真正的难题是反哺机制（详见[[wildlume-feedback-product|反哺机制-A方向]]）
- 不追求真实买家画像（隐私拿不到也不该追求），做行为画像和场景画像即可

## 五、信息流四类盘点的优先级判断

按"最薄弱 × 最高杠杆"排序：

1. **下游**（最高杠杆）——ERP 已有数据回流雏形，差最后一公里就能形成完整闭环
2. **终端**（最痛但难度高）——曜野独立性基础设施的真正命门；大部分数据可通过下游通道获取
3. **中游**（结构性缺口）——海外仓信任、头程物流空白、多主体协同
4. **上游**（中长期）——工厂端优化更多依赖关系而不是技术

## 六、ERP 跨信息流的设计要求

来自本次推演的几个 ERP 关键设计要求（不区分模块归属，按设计原则列出）：

1. **数据模型按终态设计**——订单、评论、广告、Listing 各表都按"分销商 - 平台店铺 - SKU - 时间"为主键索引，哪怕评论/广告表暂时为空
2. **接口/字段预留**——评论的语义分类字段、广告的 ACoS 字段、Listing 的 BSR 字段先在数据库里建好
3. **权限模型按终态做细粒度**——按数据类型分权限（订单+售后 vs 评论 vs 广告 vs 定价/利润），且支持模式切换（"股东模式" vs "普通分销商模式"）
4. **品牌字段双层结构**——公司品牌 + 运营品牌
5. **批次打标字段**——用于产品改良前后的 A/B 验证
