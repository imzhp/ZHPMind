# 注意力治理

重新定义多智能体（Multi-Agent）系统设计的核心框架：Agent 不是角色（身份标识），而是注意力状态（当前的调度模式）。系统设计的真正问题不是"谁负责什么"，而是"当前系统最应该关注什么、能调用什么、能修改什么、在哪里执行、如何根据反馈调整"。**六种边界**的显式设计决定了系统的真实能力。

## 定义

**注意力治理（Attention Governance）**：在多 Agent 系统中，通过显式设计每个 Agent 的上下文范围、工具权限、状态边界、执行环境、反馈机制和记忆策略，实现对系统认知资源的结构化治理。

公式化定义：

> **Agent = 注意力范围 + 上下文范围 + 工具范围 + 状态范围 + 环境范围 + 反馈范围**

与角色化分工的根本区别：

| 角色分工（Role Division） | 注意力治理（Attention Governance） |
|---|---|
| 谁负责什么？ | 当前系统最应该关注什么？ |
| 名字区分 Agent | 边界区分 Agent |
| 产品隐喻 | 系统架构 |

## 注意力状态模型

Agent 的本质不是身份，而是**注意力状态**——每步行动之前，系统如何决定什么信息重要、什么工具该打开、什么状态不能被污染：

| 状态 | 优先关注 |
|---|---|
| **研究状态** | 证据、来源、质量、不确定性 |
| **写作状态** | 结构、表达、节奏、读者路径 |
| **审查状态** | 漏洞、反证、风险、过度断言 |
| **执行状态** | 工具调用、环境变化、执行结果、错误反馈 |

同一个模型切换到不同注意力状态，比"四个叫不同名字的 Agent"更接近系统的真实运作方式。

## 六种边界

Agent 的能力由其边界决定，共有六种：

**上下文边界（Context Scope）**
此刻能看什么，不能看什么。上下文太脏，模型再强也会被带偏。Review Agent 只能看成稿、看不到原始证据链，审查就只是文本评论。

**工具边界（Tool Scope）**
能调用什么，哪些动作需要确认。工具不是能力列表，而是行动边界。Agent 能行动意味着能改代码、删文件、调 API、写数据库——权限意味着风险，风险意味着隔离。

**状态边界（State Scope）**
能修改什么，谁能覆盖主状态。没有状态边界，多 Agent 就是多人同时改同一份文件。

**环境边界（Environment Scope）**
在哪里执行，错误会不会污染真实环境。代码、数据库、浏览器和 API 都不是纯文本空间——沙箱、回滚机制、人工确认是必要的设计。

**反馈边界（Feedback Scope）**
如何知道自己错了。评论不是验证——测试、日志、事实校验才是真正的反馈。让模型互相评论产生的是安全感，不是安全性。

**记忆边界（Memory Scope）**
什么进入下一轮，什么应该丢弃。没有记忆无法积累，记忆失控会污染整个系统。

## 拆分 Agent 的判据

是否拆 Agent，看边界是否真正不同：

**应该拆（边界确实不同）**
- 需要不同上下文
- 需要不同工具权限
- 会修改独立环境
- 需要独立验证
- 目标函数天然冲突

**不应该拆（没有边界差异）**
- 上下文相同、工具相同、状态相同，只是说话风格不同 → 那不是多 Agent，那只是多 Prompt

## 操作系统隐喻

最匹配注意力治理框架的心智模型是**操作系统**，而非公司组织图：

- 操作系统管理认知进程，不是管理 AI 员工
- 操作系统关心：谁能读取哪些上下文？谁能调用哪些工具？谁的错误会不会污染主环境？谁的结果必须经过验证才能进入下一步？
- 操作系统不靠角色名实现可靠性，靠调度、权限、隔离、状态和反馈实现

用户界面可以呈现角色；底层系统必须实现边界。
