# 曜野 Project 推进框架

> 本文档是 2026-05-20 对话推演的沉淀产物。基于"框架驱动而非主题驱动"的工作方法论修正,提出完整的 Project 推进路线图。
>
> **核心修正**:先完成所有模块的 v1 骨架(Phase 1,2-3 个月),再在完整框架上选择性深挖(Phase 2,持续)。
>
> **本版本范围**:三层框架、Phase 1 任务清单、开新对话标准化做法
> **下一版本**:Phase 1 完成后,基于全景重新评估 Phase 2 的优先级

---

## 一、完整框架的三层结构

之前的工作只覆盖了业务层的部分内容(业务架构 v1 + 反哺机制 A/B)。完整的曜野 Project 框架应该是三层:

```
层级 1:业务层(Why & What)
├── 业务架构(战略骨架 + 信息流/资金流/产品流盘点)
├── C 端反馈反哺机制(A/B/C/D/E 5 方向)
├── 选品方法论
└── 核心痛点的解决方案(选品 / 库存周转 / 售后)

层级 2:流程层(How)
├── 标准化流程(采购/出口退税/海外仓对接/售后...)
├── 跨主体协同流程(4 家公司之间)
├── 跨方协同流程(曜野 ↔ 分销商/供应商/货代)
└── 决策流程(选品决策/定价决策/库存决策...)

层级 3:基础设施层(With What)
├── ERP 系统(模块、字段、权限、集成)
├── 协作工具(飞书 / 企业微信 / 微信 的角色分工)
├── 知识库(Obsidian + Claude Project + 内部文档)
├── 数据层(采集、聚合、分析、可视化)
└── AI 应用层(在各环节的具体介入点)
```

**关键洞察**:层级 2 和层级 3 必须等层级 1 完整后才能合理设计。在不完整的业务架构上设计 ERP 或选型协作工具,会反复返工。

---

## 二、推进策略:Phase 1 + Phase 2

### Phase 1:完成骨架(2-3 个月)

**目标**:每个模块做"v1 骨架版",求全不求深。最终交付一份完整的"曜野业务全景地图"。

**为什么先做骨架**:
1. 依赖关系明确——业务架构 v2 不完成,后面的反哺机制、ERP、协作工具都缺底层依据
2. 决策连贯性——决策者(张昊鹏)需要看到全貌才能做合理取舍
3. 防止反复返工——基础设施层的设计要求看完整业务图景

### Phase 2:填充深挖(持续)

**目标**:在完整框架上选择优先级最高的模块深入推。每次深挖都有清晰的全局坐标。

## 四、开新对话的标准化做法

每次开新对话遵循以下流程:

### 1. 判断对话类型

| 类型 | 特征 | 是否新开 |
|------|------|---------|
| **推演型** | 思考产出、可能发散、目标想清楚某事 | 视情况(主题切换时新开) |
| **产出型** | 单次交付、目标做出一份可用文件 | 一定新开 |
| **学习型** | 长期持续、多次对话、能力建设 | 一定新开,独立主线 |

### 2. 准备启动包

启动包包含:
- 任务目标
- 成功标准
- 参考材料(指明带哪些文档过去)
- 张昊鹏需要在新对话开场补的信息
- 备注(节奏/风格/特殊约束)

### 3. 沉淀产出

每个推演型对话结束时,沉淀一份 v1 文档归档进 Obsidian。文档结构参考:
- 元数据(版本、日期、关联文档)
- 一、本质/核心判断
- 二、详细设计
- 三、对照参考(和其他模块的关系)
- 四、落地抓手清单
- 五、待续(v2 应深挖的内容)

### 4. 更新全景

每完成一个板块就回到本文档更新进度,确保不丢失整体脉络。

## 六、风险与注意事项

### 6.1 不要分散精力

短期(1-2 周内)不建议再开新对话。现有 3 个新对话 + 日常业务已经接近精力上限。等当前对话出第一批产出后再开新的。

### 6.2 不要为了快而牺牲质量

Phase 1 求全不求深,但"骨架版"也要保证逻辑自洽,不能为了对话数量牺牲质量。每个 v1 文档要能站得住脚。

### 6.3 不要跳过依赖

任务清单按依赖排序。如果跳序,可能要返工。例如先做 ERP 整体架构再做业务架构 v2 会卡壳。

### 6.4 定期校准

每完成 3-5 个任务回到本文档校准一次。如果发现路线偏了,及时调整。
