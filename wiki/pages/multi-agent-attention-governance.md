# 多 Agent 的本质不是分工，而是注意力治理

一篇拆解多智能体（Multi-Agent）系统设计误区的深度文章。大多数产品把 Agent 设计成角色——研究员、写手、审查员——但真正决定系统能力的不是角色名，而是上下文边界、工具权限、状态隔离和反馈机制。核心论断：**多 Agent 的本质不是分工，而是[[attention-governance|注意力治理]]。**

## 角色化的诱惑

人们自然地把多 Agent 设计成角色，有三个原因：

1. **组织隐喻的习惯**：人类理解复杂协作最熟悉的方式就是分工——一个人研究，一个人写作，一个人审查。这个模型太顺了。
2. **产品化的需要**："一个 AI 团队帮你完成任务"显然比"一个上下文路由系统根据任务状态动态调度工具、记忆和执行环境"更好卖。
3. **Prompt 时代的延续**：过去写"你是一名资深产品经理"，现在自然变成"你是 Research Agent"。

角色适合给用户看，降低理解成本。但**产品翻译不能替代系统架构**。如果系统内部只是几个 role prompt 在互相传话，那就不是多 Agent 架构，而是多角色剧本。

## 角色名不等于系统边界

角色化的核心误区：把"角色名"当成了"系统边界"。

一个典型案例是 Review Agent。写作 Agent 生成文章，Review Agent 负责审查，听起来合理。但如果 Review Agent 只能看到成稿、看不到原始资料和事实来源、也没有阻止发布的权力——它所谓的审查只是文本评论，不是真正的审查。Review Agent 这个名字制造的是**安全感**，不是**安全性**。

真正的分工不是把名字拆开，而是把边界拆开。人类组织分工有效，是因为不同岗位背后有不同经验、权限、责任、信息渠道、评价标准和风险承担。但很多多 Agent 系统里，所谓不同角色看到的是同一批上下文、调用同一批工具、修改同一个状态——那只是不同人设。

**角色不是能力，边界才是能力。**

## Agent 是注意力状态，不是身份

这里的"注意力"不是 Transformer 中的注意力机制，而是每步行动前的调度问题：系统如何决定什么信息重要、哪些工具该打开、哪些状态不能被污染。

更准确的理解：**Agent 是一种注意力状态，而非一种角色身份。**

- 研究 = 注意力状态：系统此刻优先关注证据、来源、质量和不确定性
- 写作 = 注意力状态：系统此刻优先关注结构、表达、节奏和读者路径
- 审查 = 注意力状态：系统此刻优先关注漏洞、反证、风险和过度断言
- 执行 = 注意力状态：系统此刻优先关注工具调用、环境变化、执行结果和错误反馈

角色分工问"谁负责什么"；[[attention-governance|注意力治理]]问"当前系统最应该关注什么"——底层逻辑完全不同。

## 六种边界

[[attention-governance]] 框架定义了 Agent 必须设计的六种边界：

| 边界 | 含义 | 失控后果 |
|---|---|---|
| **上下文边界** | 此刻能看什么，不能看什么 | 上下文太脏，模型被带偏 |
| **工具边界** | 能调用什么，哪些动作需要确认 | 权限泄漏，不可控行动 |
| **状态边界** | 能修改什么，谁能覆盖主状态 | 多 Agent 同时改同一份文件 |
| **环境边界** | 在哪里执行，错误会不会污染真实环境 | 沙箱缺失，操作真实系统 |
| **反馈边界** | 如何知道自己错了（测试、日志、事实校验） | 只有模型互相评论，无真正验证 |
| **记忆边界** | 什么进入下一轮，什么应该丢弃 | 记忆失控污染系统 |

**Agent = 注意力范围 + 上下文范围 + 工具范围 + 状态范围 + 环境范围 + 反馈范围**

## 何时真的应该拆 Agent

只有边界真正不同时才值得拆：
- 需要不同上下文 → 值得拆
- 需要不同工具权限 → 值得拆
- 会修改独立环境 → 应该拆
- 需要独立验证 → 应该拆
- 目标函数天然冲突 → 应该拆

反之，如果几个 Agent 看到同样的上下文、用同样的工具、修改同样的状态，只是说话风格不同——**那不是多 Agent，那只是多 Prompt。**

## 操作系统隐喻

好的多 Agent 系统更像操作系统，而不是公司组织图。公司组织图关心责任分配（谁负责什么）；操作系统关心资源治理（资源如何调度、权限如何分配、进程如何隔离、异常如何恢复）。

操作系统需要：调度注意力而非堆角色；管理上下文而非塞满上下文；控制权限而非开放所有工具；隔离环境而非直接污染主系统；记录日志而非只留下最终答案；处理反馈而非让模型互相评论。

这与 [[fat-skills-thin-harness]] 的原则一脉相承：系统可靠性来自对权限、隔离、状态和反馈的精确控制，而非来自角色命名。见 [[agentic-engineering]] 对 Agent 工程纪律的整体框架。
