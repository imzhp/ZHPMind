# skill: adversarial-review

## 设计意图

让 AI 扮演**对立专家**,从专家视角挑战一段方法论 / 一份知识结构 / 一组判断的合理性,把里头错的、过时的、不完整的、纯话术的内容暴露出来。

这是 ZHPMind 红线"cross-modal eval"(多模型互评)之外的另一种增强:**cross-role eval**——同一个模型扮演不同立场互评。两者作用机制不同:
- cross-modal:换模型,看不同训练分布下结论是否稳定
- cross-role:换视角,看同一份结论在对立立场下是否站得住

对学习者尤其重要——**没有实操的人,反驳是唯一的"现实检验"机制**。

## 来源

- **原型**:云飞扬 AIFirst 微博(2026-05-23)蒸馏自己亚马逊课程时的 prompt 片段
- 原话:"你现在是计算广告专家的角色,你熟读整个行业内所有关于电商搜索广告的一些底层的算法,你设计过谷歌、淘宝、京东、亚马逊这些底层的购物广告算法,通过这些去拆解这篇文章或者这份知识结构的一些可以去反驳的问题"
- **泛化**:在 ZHPMind 设计原则下,把这种"指定对立专家身份 + 系统性挑刺"的手法提炼成通用 skill

## 适用边界

### 适用
- 方法论审稿(method 类页面)
- 判断框架审稿(framework 类页面)
- 课程 / 书籍 / 行业报告的内容审视
- 自己写的策略文档 / 决策书 / 项目方案,在 finalize 前过一遍
- 学习者蒸馏外部课程时(主要场景)

### 不适用 / 慎用
- **事实类知识**(年份、数据、定义、API 参数)——直接核对官方源就行,不需要 adversarial
- **个人体验 / 反思类**(reflection 类页面)——这种页面的"真实性"不需要专家挑战,挑战反而失真
- **创作类内容**(寓言、文学、艺术评论)——adversarial 会把多义性挑成单一性

### 关键风险

1. **模型版本敏感**:Opus 找到的问题远比 Sonnet 多;Haiku 几乎不出货。建议**用 Opus 跑**,Sonnet 作为快速过滤。
2. **AI 容易硬挑**:你给它一个对立身份后,它可能为了"看起来在工作"硬找问题。Prompt 里明确"找不到就说找不到"是必须的纪律。
3. **专家身份要具体**:"资深运营专家"这种泛指会出空话。要给具体履历("设计过谷歌、亚马逊的购物广告算法"这种)。

## 使用方法

### 基础用法
把下方完整 prompt 复制到对话,替换 `{对立专家角色}` 和 `{待审材料}`。

### 进阶用法(集成进 ZHPMind 学习工作流)
1. 写完一段方法论草稿后,跑这个 skill
2. 把输出的质疑清单存到对应项目的 `adversarial-review.md`
3. 对每条质疑,做决策:接受 → 修改方法论;拒绝 → 在质疑后写"驳回理由"
4. **驳回的质疑也要留档**——它代表你"明知道有人会这么质疑,但选择不接受"的判断,未来打脸时可以回头看

## Prompt 模板

```markdown
你是 {对立专家角色}。

【对立专家角色示例,挑一个最贴近的填入】
- 一位设计过谷歌、亚马逊、京东购物广告底层算法的资深计算广告专家,熟读整个行业关于电商搜索广告的所有公开论文和专利
- 在 {行业} 做了 20 年实操、亲历过 2008 金融危机和电商崛起两个完整周期的资深从业者,带过 5 个不同公司的同类项目
- 一位刚从 {公司} 同岗位离职、对该公司内部数据和真实做法了如指掌的前员工
- 一位写过 3 本 {领域} 教科书的学术专家,关注理论严谨性和实证证据

我会给你一段方法论 / 一份知识结构 / 一组判断。你的任务是从你的专家视角挑战它。

## 一、立场

你不是来认可的。**默认假设这套内容里至少有 30% 是错的、过时的、不完整的或者只是话术**。你的工作是找出来。

但**你也不是来硬挑的**。找不到问题的部分,直接说"这条没找到问题",不要为了显得在工作而硬挑——硬挑的质疑没有价值,会污染审稿质量。

## 二、审视维度

### 1. 内部逻辑
- 概念定义是否精确?有没有把不同层级的东西混在一起讲?
- 因果链是否成立?有没有"相关性当因果性"的地方?
- 是不是在用循环论证?

### 2. 外部参照
- 行业共识跟这套内容冲突的地方在哪?
- 平台官方文档 / 公告里有没有反例?
- 头部实操者的公开做法跟这套内容一致吗?

### 3. 时间维度
- 哪些观点在 N 年前成立,但平台规则 / 技术 / 用户行为变了之后已经不成立?
- 哪些是"过去 A 现在 B"的迁移,但作者还在用 A 思维?

### 4. 完整性
- 跟这个内容同等重要的东西,作者是不是漏讲了?
- 反例(什么时候这个方法不适用)有没有讲?

### 5. 话术识别
- 哪些段落是"为了完整性凑数",实操中根本用不上?
- 哪些是"听起来很对但没有可操作 handle"的空话?

## 三、输出格式

对每条质疑:

```
[质疑编号] [严重: 🔴错误 / 🟠过时 / 🟡不完整 / 🟣话术]
原文观点:<引用或概括>
我的质疑:<一句话讲清楚问题>
理由:<行业证据 / 逻辑漏洞 / 反例,具体可验证>
建议修正方向:<怎么改>
```

数量上限(防硬挑):
- 🔴 错误:最多 5 条
- 🟠 过时:最多 5 条
- 🟡 不完整:最多 5 条
- 🟣 话术:最多 3 条

找不到的类别直接写"未发现",不要凑数。

## 四、纪律

- 不要客套铺垫("作者讲得很好但是……")
- 不要重复表达同一个质疑
- 每条质疑都要给可验证的理由,不是"我觉得"
- 引用原文时用 `> ` 块引用,不要篡改原文

---

【待审材料】
{贴在这里}
```

## 跟 cross-modal eval 的关系

| 维度 | cross-modal | cross-role(本 skill) |
|---|---|---|
| 换什么 | 换模型 | 换视角(同一模型) |
| 适用 | 事实类、技术类、有标准答案的 | 方法论、判断框架、无标准答案的 |
| 成本 | 高(多次 API 调用) | 低(一次调用) |
| 互补关系 | 验事实 | 找漏洞 |

**两者不冲突,理想是都跑**:cross-modal 看事实层稳定性,cross-role 看判断层漏洞。
